# セキュリティ・ベースライン

コードを1行も書く前に決めておくべきこと。後から変更するのが困難、または事故が起きてからでは遅い項目を並べる。

---

## 1. ウォレットの役割分離

**原則: 1つのウォレットに複数の役割を持たせない。**

| 役割 | 使うアカウント | 備考 |
|---|---|---|
| 資産の保管 | Coinbase Wallet（既存） | 開発ツールに一切接続しない |
| testnet デプロイ | 開発専用 EOA `dev-deployer` | Foundry キーストアで管理 |
| dApp のユーザー検証 | Coinbase Wallet（読み取り接続のみ） | 実ユーザー目線の動作確認用 |
| mainnet デプロイ（将来） | 専用 EOA + ハードウェアウォレット | Ledger 等。`cast` は `--ledger` に対応 |
| mainnet のコントラクト owner（将来） | **マルチシグ（Safe）** | 単一 EOA にしない |

### なぜ owner をマルチシグにするのか

`onlyOwner` で守られた関数（一時停止、パラメータ変更、資金引出など）を単一 EOA が握っていると、
**その鍵が漏れた時点でコントラクトが終わる**。実際にこのパターンで数百億円規模の被害が出ている。

Safe（旧 Gnosis Safe）などの M-of-N マルチシグを owner にしておけば、
鍵1本の漏洩では権限を奪われない。Step 4 で実際に設定する。

## 2. 秘密鍵の扱い

### やらないこと

```bash
# ❌ 平文で .env に置く
PRIVATE_KEY=0x4f3e...

# ❌ コマンドラインに直接書く（シェル履歴に残る）
forge script Deploy --private-key 0x4f3e...

# ❌ コードにハードコードする
```

### やること

```bash
# ✅ Foundry の暗号化キーストアを使う
cast wallet import dev-deployer --interactive
forge script Deploy --account dev-deployer
```

キーストアは AES 暗号化され、実行時にパスワード入力を求められる。
シェル履歴にもファイルにも平文の鍵が残らない。

### .gitignore に必ず入れるもの

```
.env
.env.*
*.key
keystore/
broadcast/          # デプロイ履歴。アドレスが含まれるので公開判断が必要
cache/
out/
.venv/
__pycache__/
```

## 3. testnet と mainnet の事故防止

**最も多い事故: mainnet に向けるつもりのないコマンドが mainnet に飛ぶ。**

対策:

- RPC URL は環境変数で管理し、`foundry.toml` の `[rpc_endpoints]` に名前付きで登録する
- mainnet 向けのコマンドには必ず `--slow` と、実行前の `--simulate`（dry run）を挟む
- Chain ID を実行前に確認するのを習慣にする

```bash
cast chain-id --rpc-url $RPC_URL
```

## 4. コントラクト設計の初期決定事項

以下は**デプロイ後に変更できない**ため、書き始める前に決める。

### 4-1. アップグレード可能にするか

| 方式 | 内容 | トレードオフ |
|---|---|---|
| Immutable（非アップグレード） | デプロイしたら永久に固定 | 安全だがバグを直せない |
| Proxy（UUPS / Transparent） | ロジックを差し替え可能 | 柔軟だが proxy 自体が攻撃対象になり、owner の権限が強大になる |

初学時は **Immutable + マイグレーション設計** を推奨。Proxy は Step 4 で扱う。

### 4-2. 一時停止機能（Pausable）を入れるか

異常検知時に処理を止められるかどうか。安全側に倒すなら入れる。
ただし「止められる権限を誰が持つか」が新たなリスクになるのでマルチシグとセット。

### 4-3. 誰が何をできるか（アクセス制御）

`Ownable` で足りるのか、`AccessControl` でロール分割が必要かを設計時に確定させる。

## 5. 監査で見る観点（Step 3〜4 で実践）

| 観点 | 内容 |
|---|---|
| 再入可能性 (Reentrancy) | 外部呼び出しの後に状態を書き換えていないか。CEI パターンの徹底 |
| アクセス制御漏れ | 権限修飾子の付け忘れ。init 関数の二重呼び出し |
| 算術の丸め | 除算の順序による切り捨て。攻撃者に有利な方向に丸めていないか |
| 外部呼び出しの戻り値無視 | `call` の返り値をチェックしているか |
| オラクル依存 | 価格の取得元を操作できないか |
| フロントランニング | mempool を見て先回りされる設計になっていないか |
| DoS | ループが無制限に伸びてガス上限に達する設計になっていないか |
| 初期化とデプロイ | constructor で設定漏れがないか。デプロイ直後の無防備な瞬間がないか |

### 使うツール

```bash
slither .                    # 静的解析
forge test                   # ユニットテスト
forge test --fuzz-runs 10000 # ファズテスト
forge coverage               # カバレッジ
forge test --match-test invariant  # 不変条件テスト
```

## 6. デプロイ後の運用

- **Etherscan/Basescan での verify** — ソースコードを公開しないと誰も信用しない
- **イベント監視** — 異常な引出や権限変更を検知する Python スクリプト（Step 4 で実装）
- **インシデント対応手順の事前作成** — 何かあったときに誰が何をするかを先に決めておく
- **依存ライブラリの追跡** — OpenZeppelin の脆弱性告知を追う

## 7. テストネットの寿命に関する注意

Ethereum Sepolia は 2026年9月頃の EOL が予定されており、後継テストネットへの移行が進んでいる。
Base Sepolia はこれに追随する可能性があるため、長期プロジェクトでは移行計画を持つこと。

現時点（2026年7月）では Base Sepolia は問題なく稼働している。
